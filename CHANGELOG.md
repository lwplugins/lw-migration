# Changelog

## [1.0.2] - 2026-10-30

### Fixed
- Uploading a backup for restore no longer stops with "The server answered with error 406" on hosts whose firewall refuses raw binary request bodies: each part is now sent as an ordinary file upload, and the part size also stays within the server's upload_max_filesize.
- A stopped upload can be cancelled from its own card ("Cancel the restore"); the job's Cancel button was below the fold, behind the drop zone.

### Changed
- The Backup section shows "Calculating…" instead of a total while the sizes are still being counted, so the figure no longer changes a few seconds after the page opens.
- The overview's second backup button is called "Custom backup", as it opens the backup options.
- The Settings page shows where the default backups folder is (the random end of its name stays hidden) and says when notification e-mails are sent.
- Backups made from the admin keep the e-mail addresses by default, so a copy restored at a test address keeps the admin's working address. Replacing them can be switched on under Advanced; the command line keeps replacing them by default.

## [1.0.1] - 2026-10-29

### Fixed
- Backups no longer stop on hosts that disable PHP's `link()` or `ignore_user_abort()` function; files are copied instead.

### Security
- A destination's stored password is only used with the server it was saved for, also when saving the destination fails or a backup runs while it is being edited. Such a destination asks for the password again instead.
- Command-line output and the job log show control characters from archive contents and connected sites as visible escapes.
- Updated development dependencies.

## [1.0.0] - 2026-10-11

### Added
- Back up the whole site (database, media, plugins, themes, must-use plugins) into one archive in the .wpress archive format, with optional gzip or bzip2 compression, an optional password and search-and-replace pairs; media, themes, plugins, must-use plugins, the cache folder, spam comments, post revisions, chosen folders and tables or the whole database can be left out.
- Restore or move a site from an uploaded file, an http(s) address or a backup already on the server, after a summary of what changes. Addresses, paths and e-mail domains are rewritten for the new site, serialized data included, and the current database is backed up first by default. Existing .wpress backups can be restored.
- Backups list: download, restore, label, browse the files inside and delete, with retention rules by number, total size and age.
- Long jobs run in short, resumable steps, so they finish on hosts with short time limits and small upload limits; uploads go in slices that shrink when the server refuses a large request.
- Scheduled backups: up to 20 schedules (hourly to monthly, in the site's time zone) with their own retention, a run log and e-mail notifications; a server cron can drive them with `wp lw-migration schedule run --due`.
- Backups folder: keep the backups in a folder of your choice, best outside the web root; moving them is a resumable job that can be finished or undone.
- Transfer links: a link to one backup that another site can restore from without a login here, valid for 5 minutes to 7 days, revocable and shown only once.
- Multisite networks: back up the whole network or chosen sites, and restore network, site and single-site backups into a network, each site at its own new address.
- Connected sites: pair two sites with a one-time code, then push this site there or pull that site here, directly between the two sites, with signed requests and an e-mail to the admins on every new connection.
- Reset tools: delete the other plugins, reset the themes, empty the media library, reset the database to a fresh install, or everything at once; each asks for your password and backs up the whole site first by default.
- Cloud destinations: upload backups to Amazon S3 and S3-compatible storage (Backblaze B2, Wasabi, Cloudflare R2, DigitalOcean Spaces, Hetzner Object Storage, Scaleway, MinIO and others) from a schedule, from `wp lw-migration export --to=…` or with "Upload…" in the backups list, in resumable parts that survive short time limits. Each destination keeps its own retention and prunes only this site's own backups; one failing destination does not stop the others, and the local copy is deleted (when you choose so) only after every upload succeeded. Backups in the cloud can be listed, restored, downloaded back or deleted. Credentials are stored encrypted and never shown again. Also WebDAV (Nextcloud in resumable parts, any other WebDAV server in one request), FTP and FTPS, and SFTP with a password or a private key and passphrase; an SFTP server's host key is confirmed once and checked before every login.
- Google Drive, Dropbox and OneDrive destinations: connect through the LW app without registering an app — the LW sign-in service at auth.lwplugins.com passes the sign-in and the token refreshes and keeps no tokens and no account data; the refresh token stays sealed on the site — or, with "Use your own app", through your own app at the provider (with PKCE and a single-use state either way). Resumable uploads that ask the provider where to go on, restore, retention, and a mail when an account must be connected again; a passing outage of the sign-in service never asks for a new connection. Dropbox and OneDrive never overwrite a file of the same name.
- Cloud destinations on the Backup form: tick where a manual backup should go, and choose whether to keep the local copy (it is deleted only after every upload succeeded); the same as `wp lw-migration export --to=… --[no-]keep-local`, and the destination's retention applies afterwards.
- A cloud upload part whose request dies twice stops only that destination, also when a passing failure came between the two deaths; the other destinations still get the backup.
- Overview: the admin screen opens on a home page with the newest backup and where it is kept, the days with a backup among the last 14, a plain note when the last scheduled backup failed, an upload failed, the newest backup is late or a job is running, what needs attention, quick actions (back up now, started right on the page; restore; move between sites), a 30-day history, the cloud destinations, the next scheduled run and the connected sites. Its endpoint only reads, and it shows no secrets.
- WP-CLI commands for every feature (`wp lw-migration`).
- React admin screen under LW Plugins → Migration (Network Admin → Settings → Migration on a network), with a Hungarian translation.

### Changed
- Backup section: a bar shows what the backup is made of and each choice shows its size, measured with the export's own filters; the sizes read "at least" while the count is still running and "could not be counted" when it gives up, and spam comments and revisions are shown as counts; after a restore or a reset the site is measured anew. Cache folders are left out by default in the web form, the Overview's "Back up now" and new schedules; the command line includes them unless `--exclude-cache` is given.
- Restore section: three steps (Source, Check, Restore) with four sources (a backup on the server, an uploaded file, an http(s) address, a cloud destination) and a check that sets the archive beside this site, read from its headers without extracting anything; facts an archive does not tell (as in one made by another .wpress tool) are shown as unknown and never block the restore. "What gets replaced" follows network and subsite restores, compressed and encrypted archives show their stored sizes, the safety backup switch says why it cannot be on when the free space is short, the importing administrator's login is kept, and "Restore now" waits for the typed address of the site that gets replaced. The backups list tags encrypted backups and backups made on another site.
- Backups section: a storage strip (this plugin's backups, the other .wpress tool's folder, free space and the retention rules that delete backups by themselves), filter chips with counts and a search, a list grouped by day showing where each backup lives, and a panel for the chosen backup with its actions, facts, label, copies per destination, transfer links (create, expiry, revoke) and contents read from the archive's headers for that backup only; a backup that vanished meanwhile answers "backup missing" without breaking the panel.
- Schedules section: a ruler of the next 7 days with one lane per schedule and a note when two runs are due in the same minute, a WP-Cron box with the server command and a Copy button, cards with the next runs, the last 14 results (with the reason a run failed) and what is backed up and where, progress on a running card, Duplicate in the card's menu, three starters when there is no schedule, and an editor that opens as a sheet with a sentence in plain words and a preview of the next runs.
- Running job card: what kind of job it is, its title, when it started and how long it has run; the large percentage beside what is happening now; a line with one segment per phase, the finished ones solid and the current one moving (still under reduced motion), a phone naming only the current phase; a note to keep the tab open, and Cancel with its confirmation inside the card, without a dialog. Past the point of no return Cancel is off and the note says why; a stopped job shows a warning strip, when it last made progress, Continue and Cancel.
- Destinations section: one card per destination with its state, where it keeps the backups and its facts; the backups there, the edit form, the delete confirmation and a host key or certificate to confirm open inside the card, one at a time. New destinations are added inline from a shelf grouped by how you get in (a sign-in, an access key, your own server): the picked place opens as a draft card below it with a live line of where the backups will go, and a saved server or storage gets its connection checked on its new card at once. No dialog opens on this screen; a type this site cannot use, or every type at 20 destinations, stays on the shelf with the reason.
- Reset section: the five tools are tiles under "What do you want to reset?", each with what it would remove (a tool the site cannot run shows why). Choosing one shows the layers of the site (plugins, themes, media, the database) with what goes struck through and what stays, what no reset touches below them, and beside it the steps before the start (the backup, your password, the site address for the database and everything), each ticked when done, and the one start button. The password is asked for only after you see what goes; too many wrong passwords replace the steps with the lock. For the database the plugins and the media are shown as staying on disk (switched off; the library emptied). Another choice starts the steps over (the backup on, nothing typed, no earlier refusal; the password is kept), and the choice holds while a start is on its way. No dialog opens on this screen.
- Backups and Restore lists: a destination's listing also records the backups it holds byte for byte as held there, so a destination added again over its old folder gets its "Also at" chips back; each connected destination is listed once per page load, and the list reloads only when a record changed.
- Admin menu: the Migration entry shows how many backups there are, in the menu's count bubble.
- Destinations section: the places to add are lists, one row per place (no wrapping tiles), and Backblaze B2, Wasabi, Hetzner and Scaleway show their own marks.
- Destinations: a new destination's folder (the S3 prefix, the FTP, SFTP and WebDAV folder) starts as the site's name, and a Google Drive, Dropbox or OneDrive account keeps this site's backups in its own folder (`LW Migration/<site>`, `<app folder>/<site>`), which the card and the draft show. On a shared account the sites do not list or prune each other's backups; a site administrator who can run code can still reach the other folders with the stored access, so only separate accounts (or the own-app option) keep them apart.

### Security
- Every answer of a connected site is signed with the connection's key over the request it answers, its status and its body, and an unsigned or changed answer is refused; a pulled archive is checked against the SHA-256 in the other site's signed answer before anything is imported, so on an http connection a network attacker cannot swap the pulled site (#1).
- An http connection is warned about on the pairing screen, the connection list, before a push or pull and in WP-CLI: the whole site travels unencrypted, so anyone on the network between the two sites can read it on the way (#1).
- Connections and imports from an http(s) address never reach link-local addresses (the cloud metadata service), carrier-grade NAT, benchmark, multicast or reserved ranges, and reach loopback and private addresses only where WordPress allows the host; the address is checked once and the request is pinned to it, so a second DNS answer cannot redirect it, and every redirect of an import is checked the same way (at most 5). A pairing code that names the other site by an IP address is refused unless the `lw_migration_allow_ip_link_hosts` filter allows it (#2).
- A password, key or secret saved for a FTP, FTPS, SFTP, WebDAV or S3 destination is forgotten when its server changes (host, port or security; the address's scheme, host or port; the storage address, provider or account), so it is never sent to another server and has to be entered again; saving other settings keeps it (#3).
- FTPS checks the server's certificate and name before the password is sent, through cURL to the checked, pinned address; a certificate no certificate authority vouches for (a self-signed one) is shown with its SHA-256 fingerprint at the connection check, confirmed once in the admin or with `wp lw-migration destination test <id> --trust-certificate=<fingerprint>`, and only that certificate's key is accepted afterwards. A confirmed certificate is forgotten when the server changes. FTPS needs PHP's cURL with FTP and TLS support (#5).
- Deleting a Dropbox destination or a Google Drive destination with your own app, changing its Client ID, mode or sign-in settings, or connecting it again withdraws the old sign-in at the provider first (Google's revoke endpoint with the refresh token; Dropbox's token revoke with the access token, refreshed first if it expired), so its tokens no longer work anywhere; when that fails, for Google Drive through the LW app (Google would withdraw the access of every site using the LW app with that account, so it is never withdrawn from one site) and for OneDrive (which has no way to do so), the delete answer, the destination card and `wp lw-migration destination remove` say where to remove the app's access in your account. A sign-in another destination of the site still uses with the same account and app is kept; when Google named no account for one of them, nothing is withdrawn and you are told where to remove the access. Uninstalling stays offline; the readme and the delete dialog say how to remove the access by hand (#6).
- Connecting a Google Drive, Dropbox or OneDrive destination records which account it is, asked straight at the provider (Google Drive's user permission id, the Dropbox account id, the OneDrive drive id). Through the LW app every refreshed sign-in is asked again at the provider, never through the LW sign-in service, before it is kept: one for another account, or one whose account the provider refuses to name, is not kept and the destination asks to be connected again, so the sign-in service cannot switch a destination to another account; while the provider is unavailable nothing is kept and the refresh is tried again later. A sign-in with your own app comes straight from the provider and is not asked again (#12).
- `wp lw-migration destination connect` prints a link to the plugin's page that works once, within 10 minutes, only for the administrator given with `--user`; the page starts the sign-in in that browser's login session, so a leaked link cannot be used to connect another account (#12).
- A transfer link is bound to the file it was made for (its size, modification time and inode, the same as the download's ETag) and dies when the file is another one under the same name (a backups folder moved to another disk keeps its links: they follow the verified copy), and every delete of a backup (the backups list, `wp lw-migration delete`, retention, the local copy removed after a cloud upload) revokes its links, so a file of the same name that turns up later cannot be downloaded through an old link (#8).
- Published backups are owner-only (0600) and the storage folder and the default backups folder 0700, whatever the umask, so other accounts on a shared server cannot read them; downloads go through PHP, so the web server needs no read access. A host that needs group read can return 0640 from the `lw_migration_backup_file_mode` filter (anything wider is cut back to 0640). A backup moved into the folder or fetched back from a cloud destination gets the same mode, from the first byte on, whatever the mode of the source and also when a hard link stands in for the copy (#4).
- The folder you choose for the backups only holds them: the backups always go into a new folder inside it with an unguessable name (`lw-migration-backups-` and 12 random characters), also where the folder is not recognised as part of the website, so even a served folder that is not recognised does not expose them at guessable addresses. A new folder you type is created together with it; choosing a folder of another site's backups as the holder is refused. A folder that holds `index.htm`, `index.shtml`, `default.htm`, `default.html`, `default.php` or `.user.ini` counts as served too (#11).
- An import grows the disk use by at most the free disk space it found before its first extracted byte, minus 256 MiB or 5 % of it, whichever is more. Every restored file and the extracted database file count against that one total (every byte counts while it is written; once a file has replaced an existing one, the old file's size is given back, so restoring a site over itself on a nearly full disk still finishes as long as each file fits beside the one it replaces), also over many requests (the password check of an unsigned encrypted archive may use only what is left), and the import stops with a message before the limit, so a small archive that inflates (a gzip or bzip2 chunk can grow about 1,000 to 10,000 times) cannot fill the disk. `wp lw-migration extract` stops the same way. When the free space cannot be read, the limit is 50 GiB, changeable with the `lw_migration_max_extract_bytes` filter. The size in an entry's header is its stored (compressed) size, so it does not bound what a compressed entry writes; this total limit does (#9).
- The database import checks, before any statement of the archive runs, that the connection reads statements in a safe character set on both sides (`character_set_client` as well as `character_set_connection`) and that the session's sql_mode has neither NO_BACKSLASH_ESCAPES nor ANSI_QUOTES once it was cleared, and stops otherwise; the views created after the swap run on the same checked session. A view in the archive that reads another database (`` `db`.`table` `` or db.table with another database than the site's), or whose statement cannot be checked for that, is skipped with a warning and the import goes on (#14).
- The pairing code and an archive password need not be typed on the command line, where other users of the server see them in the process list and the shell history: `wp lw-migration link add` without `<code>` asks for the code (a hidden prompt on a terminal, otherwise one line on standard input), and `export`, `import`, `extract` and `cloud restore` take `--password-file=<path>` (size-capped, the path is never printed) or, without a terminal, `--password` with the password as one line on standard input; one trailing line ending is cut, an empty password is refused, and `--password` together with `--password-file` is an error. `<code>` and `--password=<value>` also work, with that warning (#7).
- A storage server's XML answer in UTF-16 or UTF-32, with a NUL byte, with a DOCTYPE or not starting with a tag is refused before it is parsed, so the DOCTYPE and ENTITY guard cannot be bypassed by an encoding trick (#10).
- Rewriting addresses inside serialized data that is itself serialized again searches the nested parts in place and stops at 32 levels and at four times the value's size: a deeper or larger part is kept exactly as it was, its lengths still valid, and the import names its table and column once in a warning, so a crafted or runaway value cannot exhaust the memory and stall the import.
- A CREATE TABLE of an archive runs only as one statement: a `;` outside quoted text, other than the one at its end, refuses it, so no second statement can ride along after the table.
- An INSERT of an archive accepts a hex value only with a lower-case `0x` prefix (the dump writer's own form); MySQL reads `0X…` as a name, not a value, so it is refused. `X'…'` and `x'…'` stay accepted.
- A CREATE TABLE of an archive runs only when every column default is a literal, NULL, the current date or time (also after ON UPDATE), UUID() or UUID_TO_BIN(UUID()), and its generated columns and CHECK constraints call only pure string, number and JSON functions. Any other function or expression, or an expression as a key part, skips the table and the import names it in a warning, so a table definition cannot make the server run a function such as SLEEP() or LOAD_FILE().
- The build and release workflows run with read-only repository access (only the release job may write), the third-party actions are pinned to a commit, and the failure artifact of the end-to-end tests includes no backup file (#13).
- The readme, the README, the password help in the Backup form and in the schedules, and `wp lw-migration export --help` say that the archive password protects confidentiality only: use a long, random password, a changed archive is not detected cryptographically, and backups belong on trusted storage (#15).
